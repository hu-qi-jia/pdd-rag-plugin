## 一、背景

第五十六轮定的六个预置类型，在真实使用中暴露出三类毛病，前两类是**桶不对**而不是模型不行：

**1. 缺桶 → 强塞。** 实测一份真实导出（68 条问答、7 个类型）里：

- **一条都没落到「未分类」**。68 条全部被塞进六个桶之一。同时置信度 ≥0.9 的有 45 条、<0.5 的只有 2 条 ——
  **jev 落在错桶里的时候一样自信**，所以「调阈值」这个旋钮治不了它。
- **「发票」8 条 100% 挤进「售后退换」**。买家的"怎么开发票"和"怎么退货"进了同一个桶。类型集里没有发票这个桶。
- **「商品属性」吞了 39/68（57%）**，成了溢出桶：里面混着问候 15 条、笑声与乱码 6 条、
  开发者自测的话 4 条、英文 2 条 —— **27 条（40%）根本不是可分类的买家问题**，却没有一个出口。
- 用户已用「把概率阈值拉到 0.9」（默认 0.2）来补偿。代价是模糊问题被**丢弃**（落未分类）而不是被**解决**。

**2. 空桶。** 「尺码推荐」拿到 0 条。

**3. 作用域混了。**（第三类，也是本次最容易写错的一处）
同一套类型集合同时在干两件性质不同的事：**给记录归档**（这条历史问答/标答属于哪一类）
与**给查询路由**（这次该不该检索、从哪个池子检索）。
[classify.ts](../../src/background/classify.ts) 里 `classifyGated` 是两条路**共用**的实现，
`classifiableCategories` 对两者返回**同一个集合** —— 于是「尺码推荐」这种
"只该出现在意图识别里、不该有存档记录"的类型，在**历史问答与标准回答两个页面上也成了一个桶**。

用户的原话：*"历史和标准回答本来就不应该保存和记录尺码相关的，所以也不应该显示尺码的这个分类；
我并没有表示在问题意图识别的时候没有尺码推荐这个分类。"*

**4. 定类型的依据换过了。** 用户明确要求：**不要拿现有这 68 条推导类型**（其中相当一部分是自测数据），
改用行业通行的分类骨架。

## 二、目标与非目标

### 目标

1. 八个**记录级**类型，覆盖 售前 / 售中 / 售后 三段，外加一个「其他」出口。
2. **把记录级与查询级的选项集分开**：「尺码推荐」留在查询级（意图识别要它），
   不出现在记录级，也不出现在「历史问答」「标准回答」两个页面上。
3. 「其他」成为 jev 的**正式选项**，让"确认不属于业务类型"与"还没判"在界面上分得开。
4. 存量标签**原地保留**，并由既有机制自动变成待重跑，用户点一次即可重判。

### 非目标（本次明确不做）

- **不退休、不删除「尺码推荐」**，那套尺码路由（`route='size'`、尺码表文档标记、`sizeRowAvailable`、
  面板尺码生成行）**全部保持可用**。见 4.3 —— 一开始把它判成"死代码"是错的。
- 不动「未分类」的语义与位置（`filterable=false`、`position=9999`、不可改名删）。
- 不改检索排序（RRF / 时间衰减 / `FILTER_MARGIN`）。
- ~~不改 `LOW_CONFIDENCE_LINE`~~ —— 这一条**被 M9 推翻**：阈值降到 0.5 后它会把「低置信」标记顶成死码，必须跟着动。

### 反目标（做了就算失败）

- **新增类型的 criteria 彼此分不开** → 按代码注释的既定结论，判定说明含糊时**全部**类型的判断质量
  一起下降，不只是写得差的那条。这比类型少更糟。
- **存量记录因迁移出现悬空 `categoryId`** → 那些行在任何按类型过滤的检索里两边都不在，静默搜不到。
- **「其他」变成低置信垃圾场** → 模型没把握就选它，等于把"缺出口"换成"出口过宽"。
- **两个作用域的选项集又漂回同一个** → 那正是本次要修的病根，必须有测试钉住。

### 我的判断

| # | 判断 | 理由 |
|---|---|---|
| M1 | 「其他」= `kind:'preset'`、`filterable:true`、`route:'retrieve'`、criteria 非空 | 必须是 jev 看得见的选项，否则等于没做（`filterable=false` 的那一类 jev 根本看不见） |

| M3 | 迁移走**原地改名复用**，不删表重建 | 存量标签能保留；且旧 id 一一对应到新类，不需要重新映射 |
| M4 | **作用域判据用现成的 `route`，不新增字段**：记录级选项集 = `filterable && route === 'retrieve'`；查询级 = `filterable`（不变） | `route='size'` 的语义正是"答案不可复用、现场生成"——**这种类型永远不该有存档记录**，两个概念天然重合。这样 `filterAllowed` 的池子规则与打标规则也自动对齐：记录身上的标签一定是个"记录进得了池子"的类型 |
| M5 | criteria 之间**互相点出边界**（写"不含 X，那走 Y"） | U4 说的是不写代码特判，不是不写判定说明。criteria 是唯一能塑造 jev 概率的杠杆；不划边两类就完全重叠，argmax 退化成掷硬币 |

| M7 | 迁移里把被动过定义的类型 `updatedAt` 顶到**严格大于**记录的 `categoryAt` | 这是本次最易踩的坑，见 5.4 |
| M8 | **基线 = 本地 HEAD `1fc7386`（v5.0「暖纸」+ 分类三处补强）**；`origin/feat/question-classification`（`ea8bd0d`，复古极简 v3.0/v3.1 线）视为**已废弃** | 二者自 `ac5d21f` 分叉：远端 6 个提交是 2026-10-12 的复古极简 UI 线，本地 1 个提交是 2026-10-15 的暖纸 v5.0 线，晚三天且已被 `feat/warm-paper-v5-archive` 推送保存。**决定性证据**：用户真实导出的信封里带 `categories` 数组，而远端支线的 `types/transfer.ts` 里 `categories` 零命中 —— 正在跑的构建只可能出自本地 HEAD 这条线。⚠️ **绝对不要 `git pull` / merge 那个远端分支**：它会把这套 UI 与「低置信/路由守卫/导入往返」整段回退掉 |

| M10 | `PanelCategory` DTO **加 `route` 字段**，UI 用一处共享谓词过滤掉 `route === 'size'` | DTO 现在只带 `id/name/kind/filterable/position`，UI **无法**自己把「尺码推荐」筛掉。加原始字段（而非加一个派生的 `recordLevel` 布尔）与 DTO 既有的风格一致，也不把规则藏进 DTO |

## 四、目标类型集

### 4.1 八个记录级类型与判定说明

判定说明即 `criteria`，**原样发给 jev**，是本文真正的实质。每条都写了"不含什么"来划边（M5）。

| position | id | 名称 | criteria |
|---|---|---|---|
| 0 | `preset:attribute` | 商品信息 | 买家在询问商品本身的客观信息：参数、材质、产地、颜色、型号规格、尺寸、配件清单、怎么使用、能不能连接某个设备。包括"介绍一下商品/产品"这类泛泛的询问。不含价格与优惠、不含是否有货、不含下单之后的物流与售后。 |
| 1 | `preset:price` | 价格优惠 | 买家在询问价格与优惠：多少钱、优惠券、满减、有没有活动、有没有赠品、能不能便宜、讲价、是否包邮。不含改价（那属于付款）、不含是否有货。 |
| 2 | `preset:stock` | 库存与规格 | 买家在**购买前**询问是否有货：现在有没有货、某个颜色或型号或规格还有没有、什么时候补货、能不能拍下、能不能换成别的规格。与商品信息的区别是这里问的是"有没有"而不是"是什么"。不含已下单包裹的物流。 |
| 3 | `preset:payment` | 支付与发票 | 买家在询问付款与票据：能用什么方式付款、能不能用某个支付方式、改价、开发票、开票流程、发票抬头与内容。不含退款（那走退换货）。 |
| 4 | `preset:order` | 发货与物流 | 买家在询问**已经下单**的包裹：什么时候发货、催发货、用哪家快递、要运单号、物流停滞不更新、大概多久到货、修改收货地址。不含退货寄回（那走退换货）。 |
| 5 | `preset:aftersale` | 退换货 | 买家在问退换与退款：要退货、要换货、要退款、运费险、七天无理由、不想要了。不含因商品损坏或功能故障引发的问题（那走质量与维修）。 |
| 6 | `preset:quality` | 质量与维修 | 买家在反映商品本身有问题：收到就是坏的、破损、少发漏发、功能故障、用不了、要维修、问保修期限。不含非质量原因的不想要了（那走退换货）。 |
| 7 | `preset:other` | 其他 | 买家的消息**不属于上面任何一类**时选它：打招呼、感谢、表情或乱码、闲聊、与本次交易无关的问题。注意：仅仅因为你没把握而选它是错的——只有确实不属于任何业务类型时才选它。 |

**id 复用的意义**（M3）：前五个沿用了既有 id，迁移只改 `name` 与 `criteria`，存量标签原地有效。
`preset:payment` / `preset:quality` / `preset:other` 是新增 id，初始为空。

**排序即 售前→售中→售后→其他**，与 U1 的分段一致。

### 4.2 「未分类」不变

`id='uncategorized'`、`name='未分类'`、`kind='uncategorized'`、`route='retrieve'`、`filterable=false`、
`position=9999`、`criteria=''`。`filterable=false` 的含义是「恒进检索池 + 不作 jev 选项」，
它和迁移来的旧文件夹（`legacy:`）同属这一档 —— **「其他」不归这一档**。

### 4.3 「尺码推荐」：查询级保留，记录级与两个页面不可见（U7 + M4）

`preset:size` **一个字段都不改**：`kind='preset'`、`filterable=true`、`route='size'`、原 criteria、原 position。
它继续是「意图识别」的选项，于是"买家问尺码 → 走尺码表整篇 + LLM 生成"这条路由**完好无损**。

变的是**谁能看见它**：

| 作用域 | 选项集 | 尺码推荐在不在 |
|---|---|---|
| 记录级打标（捕获时 / 补分类） | `filterable && route === 'retrieve'` | **不在** —— 于是永远不会有一条记录被打上尺码标签 |
| 查询级识别（每次检索） | `filterable`（不变） | **在** |
| 「历史问答」「标准回答」两个页面 | 按上表记录级口径过滤 | **不显示** |

**为什么用 `route` 而不是新增字段**（M4）：`route='size'` 的定义就是"答案取决于买家个体参数、
历史回复**不可复用**"。既然不可复用，这种类型下就永远不该有存档记录 —— 两个概念是同一件事，
不是一个巧合。所以不需要 `scope` / `recordLevel` / 第二个开关。

**顺带对齐**：`route.ts#filterAllowed` 的池子规则是「picked 中的 `retrieve` 型 ∪ 所有 `filterable=false` 型」。
记录级只用 `retrieve` 型打标之后，**一条记录身上的标签必定是"它进得了池子"的类型** ——
打标规则与检索规则自动一致，不会再出现"标了个永远搜不到的类"。

**存量里已经被标成尺码的记录**（本机 0 条，别的库可能有）：迁移把 `preset:size` 的 `updatedAt` 顶新，
它们就会变成补分类候选被重判进八个记录级类型（见 5.4 的取法）。

**本机的一个事实（不是设计问题）**：这家店**没有上传过尺码表**（5 篇 kbDocs 无一带 `isSizeTable`），
而尺码路由的四个前提里有一个是 `hasSizeTableDoc`。所以那条路**今天**不会触发 ——
这是**配置状态**，上传一篇尺码表即可，与本次类型改动无关。

## 五、数据模型与迁移

### 5.1 不新增字段

`CategoryRecord` **一个字段都不加**：

- 作用域靠 `route` 区分（M4）；
- `filterable` 的语义不变（`true` ≡ 是 jev 的选项且参与类型过滤；`false` ≡ 恒进池、不作选项）。

唯一的 DTO 变更是 `PanelCategory` 加 `route`（M10），那是**对外表示**，不是存储。

### 5.2 `PRESET_CATEGORIES`（`shared/constants.ts`）

改成 4.1 的八条，`route` 全为 `'retrieve'`。
**`preset:size` 不在这个数组里** —— 它要保留 `route='size'`、保留原 criteria，所以仍由数组定义，
只是**排在业务类之后**（position 8，见 5.3 ⑤），并加注释说明它是"查询级专用"。

> 实现提示：数组里 `route` 字段的类型是 `'retrieve' | 'size'`，两条路都要能用。
> 若把 `PRESET_CATEGORIES` 拆成"记录级八条 + 尺码一条"两个导出，也合理 —— 但要保证
> `ensurePresetCategories` 与迁移都读到全部九条。

### 5.3 Dexie `version(9)` 迁移

```
version(9).upgrade(async (tx) => {
  ① 五个既有预置改名 + 换 criteria（preset:attribute / price / stock / order / aftersale）
  ② **先做名称唯一性守卫**：新增之前，若已有非预置行（custom / legacy:）占用了新预置的名字
     （最可能是「其他」——v8 迁移是从用户文件夹名造 legacy:* 的，且那些行 criteria:''），
     必须先把那行改名让开。理由见 5.5
  ③ 新增三条：preset:payment / preset:quality / preset:other
  ④ 重排 position：八个记录级 0..7，preset:size 排 8
  ⑤ **把全部非预置、非未分类的行 position 推到 ≥9**（见 5.6）
  ⑥ 凡是被 ①③④ 碰过的类型，以及 preset:size，updatedAt = 见 5.4 的取法
     （preset:size 也要顶：存量里可能已有尺码标签，得让它们重判）
  不做任何删除 —— preset:size 保留。
})
```

不需要新索引（`categories` 表已有 `id, kind, position`）。

### 5.4 时间戳陷阱（M7，最容易写错的一处）

`isBackfillCandidate` 的重跑判据是 `(rec.categoryAt ?? 0) < catUpdated`。
而 [db.ts](../../src/background/db.ts) 里明写着一条注意事项：

> 迁移把类型的 `updatedAt` 与标答的 `categoryAt` 写成同一个 `Date.now()`，两者相等 → `<` 不成立
> → 迁移来的标答不会被误判成"待重跑"。

**上一次迁移要的是"不重跑"，这一次要的正是"重跑"。** 所以本次迁移**必须**让被改动的类型
`updatedAt` **严格大于**存量的 `categoryAt`：

- 若沿用"同一个 `now`"的写法，criteria 改了而记录不重跑 —— **类型定义换了，旧标签却原样留着**，
  这是静默失效：用户会看到新类型列在界面上，而存量记录仍按旧标准归类。
- 做法：先读存量记录 `categoryAt` 的最大值，取 `max(now, maxCategoryAt + 1)`；或直接在
  `now` 上加一个明确的偏移。两种都行，**不能取等**。

验收手段见第七节——这一条必须有测试，不能靠读代码确认。

### 5.5 名称唯一性是硬约束，迁移必须守（见 5.3 的 ②）

`jev.ts` 里 `criteria` 是**以类型名为键**构造的（`criteria[c.name] = c.criteria`、
`idByName.set(c.name, c.id)`），同名会让后一行的 id **静默**覆盖前一行的映射。
`createCategory` 正是为此硬拦重名（[categories.ts](../../src/background/categories.ts) 约束①）。

但**迁移路径不经过 `createCategory`**：v8 从用户文件夹名造 `legacy:*` 时没有任何查重，
且那些行的 `criteria` 是**空串**。所以只要用户有个叫「其他」的旧文件夹，本次迁移就会造出
两行同名 —— 空 criteria 那行还会把「其他」的出口判据**顶掉**，等于把出口又堵上
（正是反目标里的"缺出口"和"噪声选项拉低全部类型"两件事同时发生）。

守卫做法：新增三条预置之前，先查全表名称；撞了就**把那行非预置行改名让开**
（例如追加「(旧)」），并在迁移里留下可观测的记录。为什么不改成给新预置换名：U2 已把名字定死为「其他」。

### 5.6 非预置行的 position 要推到新预置段之后

`listCategories` 按 `position` 升序、同值再按 id 排。既有的自定义类型，position 来自**旧的**
`PRESET_CATEGORIES.length`（6），`legacy:` 行则从 100 起。预置段涨到 9（八业务类 + 尺码）之后，
position 为 6 / 7 / 8 的自定义行会与预置行**同值**，而 `cat-…` 的 id 排在 `preset:…` 之前 →
它们会插进预置段内部，破坏 U1 的分段。

`createCategory` 那边不用改：它取 `max(既有自定义 position) + 1`，迁移推完之后自然接在 9 往上。

（本店当前无自定义类型 —— 7 个类型 = 6 预置 + 未分类 —— 所以这条只对别的库生效，但迁移得写对。）

## 六、分类调用侧改动

### 6.1 门禁要带作用域（本次的核心改动）

`classifyGated` 现在是记录级与查询级**共用**的实现，`classifiableCategories(cats)` 对两者返回同一集合。
把它改成带作用域：

```
classifiableCategories(cats, scope: 'record' | 'query')
  record → filterable && route === 'retrieve'
  query  → filterable                       （与今天逐字节相同）
```

三个调用点（**全部要改**，漏一个就漂回同一个集合）：

| 调用点 | 作用域 |
|---|---|
| `classifyRecord`（捕获时打标 → `classifyGated`） | `'record'` |
| `classifyForQuery`（每次检索 → `classifyGated`） | `'query'` |
| `runBackfill`（补存量，直接调 `classifiableCategories`） | `'record'` |

`classifyGated` 需要新增一个作用域参数并由上面两个入口分别传入。
**建议显式传参而不是给个默认值** —— 默认值会让"忘了传"静默地退回旧行为，正是反目标里那条。

### 6.2 `INSTRUCTIONS` 必须给「其他」留出口

现在的指令是 `'这是买家发来的消息。判断它属于哪一类问题。'`（[jev.ts](../../src/background/jev.ts)）。

**这句话与 M1 直接冲突**：模型被要求"判断它属于哪一类"，而选项里七个是业务类、
第八个是兜底 —— 不给出口，模型会本能地回避兜底项，于是"缺出口"这个病根原样保留。必须改成类似：

> 这是买家发来的消息。判断它属于哪一类问题；如果都不属于（例如招呼语、闲聊、与交易无关的内容），选「其他」。

「其他」的 criteria 里那句"仅仅因为你没把握而选它是错的"是配套的**反向**约束，两处一起才既开出口又不让它泛滥。

**注意作用域与指令的关系**：记录级与查询级的**选项集**不同（尺码只在查询级），
但可以共用同一句 `INSTRUCTIONS` —— 因为它说的是"从给定选项里选"，
选项表本身由 `criteria` 决定。是否要给两个作用域各写一句指令，留给实现者（见第十节）。

### 6.3 阈值默认值

`DEFAULT_SETTINGS.classifyProbThreshold` 0.2 → 0.5（M6）。用户真机上已手动设为 0.5，
本次把默认值对齐，避免新装用户落在 0.2 上。

### 6.4 criteria 的可区分性是硬指标

八条 criteria 要满足：**任取两条，读一遍能说出"什么句子该走 A 不该走 B"**。
验收办法见 7.3——造边界句跑实测，不是肉眼看一遍说"挺清楚的"。

## 八、面板影响

- **类型导航要过滤**（M10）：`PanelCategory` DTO 加 `route`，UI 侧用**一处共享谓词**
  （如 `isRecordLevel(c) => c.route === 'retrieve'`）过滤「历史问答」与「标准回答」两个页面的
  类型导航、筛选与「移到其他类型」选择器。**不要在这三个地方各写一遍判断** —— 一处漏了就漂。
- 「其他」会作为一个正常类型出现在这两个页面里，可手工摆放标答（`setGoldenCategoryManual` 不过滤类型）。
- 低置信标记（`isLowConfidenceCategory`）**必须随 M9 一起改**，否则它会变成死码 —— 见下。
- **这一处是审阅时才发现的三线耦合**，误判代价是静默失效：

  | 量 | 判据 | 阈值 0.5 下的后果 |
  |---|---|---|
  | 记录被打标 | `pickRecordCategory`：`p >= classifyProbThreshold` | 只有 `p ≥ 0.5` 的记录才带 jev 标签 |
  | 标记为「低置信」 | `isLowConfidenceCategory`：`p < LOW_CONFIDENCE_LINE` | 两条件**永不同时成立** → 标记恒不显示 |
  | 不许收窄检索 | `decideRoute`：`top < LOW_CONFIDENCE_LINE` → no-filter | 与"过阈值"同一判据，守卫退化成冗余 |

  也就是说：`LOW_CONFIDENCE_LINE = 0.5` 与验收地板重合之后，「低置信」这个功能**整个失效**
  （不是"少标几条"）—— `MemoryListTab` / `FoldersTab` 的标记与浮层永远不出现。
  M9 把这条共用线抬到 0.65，三个量重新各归其位。
- `isLowConfidenceCategory` 还要求 `categorySource === 'jev'`，所以手工指定的（`manual`）
  与继承的（`inherit`）本就不会被标记 —— 这条不受影响。
