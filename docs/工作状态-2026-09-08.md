## 〇-CC、2026-09-22 第五十五轮:度量埋点 + 待沉淀清单 + 导出补 kbDocs → 0.16.0(单测 580/580,tsc 0 错,e2e 34/34)

用户先说「阅读代码,以产品经理的身份来看,下一代迭代版本还可以增加哪些功能」,看完 PM 报告说「可以,先执行 v0.16 的建议。完成后提交并推送」。

三件事的共同点是**把已经有了、但说不清/接不上/搬不走的东西补齐**,不是再加一层功能:

| 交付 | 此前缺什么 |
| --- | --- |
| 度量埋点 | 工具**没有任何办法回答"它到底帮上忙没有"**。检索准不准、候选真被填过几次,全靠感觉 |
| 待沉淀清单 | 答案其实在库里(问答记录按 90 天衰退,问得越多越说明值得固化),**只是没人把它挑出来** |
| 导出补 kbDocs | 换台机器导入后块在、原文不在 ⇒ 「分块升级 → 自动重切」这条链在新机器上断掉,而原文一直在用户手里 |

### 一、度量埋点(本机计数,不出网)

- **键的口径单源** `shared/metrics.ts`:六类全局事件(`search.total` / `search.miss` / `panel.open.click` / `panel.open.hotkey` / 四类 `fill.*`)+ 逐条用量键 `item.<golden|knowledge>:<id>`。SW 写、content 上报、设置页展示三处共用这一份字面量 —— 对不上**不会报错,只会让页面上的数字永远是 0**,所以另用单测把键集合与标签一一对应钉住。
- **跨上下文的裸数据当场校验**:类型只在编译期拦得住本仓库的代码,content 发来的消息走 `isTrackableEvent` 白名单,**未知键不落库也不弹错**(统计是旁路,不该在客服面前报错)。
- **为什么 content 要专门上报**:候选填充与面板打开都在**页面里当场完成**(`fillInput` 直接写官方输入框,不经 SW),SW 没有别的途径知道发生过 —— 这不是"再多存一份",是同一件事只能由当事方记账。
- **防重复计数**:content 本地填充自己报;SW 发起的填充走 `PDD_FILL_INPUT`,由 SW 报 —— 该消息的处理器里写明"此处故意不报,否则一次填充记两遍"。
- **不拖累检索(两条硬约束)**:
  ① 计数写入**不得**使检索缓存失效 —— 否则每次检索都白重建一次全表缓存(单测直接断言"写计数前后拿到的是**同一个数组引用**");
  ② 记账一律**即发即忘**(`void db.bumpMetrics(...)`),不让一次检索多等一次 IndexedDB 写入。
- **逐条用量只记金标准与知识库**:历史记录 90 天过期,给它计数只会攒下查不到主人的孤儿键;且条目删除时它的用量键**同事务**一并删除。
- **设置页「使用统计」卡**:检索行合成 `40 次 · 未命中 10 次(25%)`;**分母为 0 时不显示百分比**(没检索过写 `0%` 是在编数字,不是结论);全 0 给空态不留一排 `0 次`;重置走内联二次确认,只清计数。卡内明写:「只记在本机,不联网、不随导出外发。」逐条用量另在文件夹页与知识库页卡片上以 `被用 n 次` 展示,**只显示 >0 的**。
- **读侧不单开消息**:计数快照随 `GET_STATS` 一起回(弹窗打开本就取一次统计),不为此多跑一趟。

### 二、待沉淀清单(新页签「沉淀」)

- **聚合是纯函数** `background/backlogPlan.ts`,`buildBacklog` 收 qa/replies/已有标准回答哈希/忽略哈希/自检会话键,**输出即全部口径**,可单测。
- **上榜**:有回复 + 还没有标准回答 + 没被忽略 + 不是自检数据。**出现次数不设门槛**,只决定排序与展示。
- **排序按次数倒序**:只按时间排会让"新问的一次性问题"盖住高频问题。同次数按最近出现时间倒序。
- **代表问题原文取最近一次**的问法(不是最早那条);回复按 `contentHash` 去重、最近优先,至多 5 条(「换一条(还有 N 条回复)」展开)。
- **提升后自动下榜**:提升用的就是清单里显示的同一个问题文本,走 `ADD_GOLDEN` 的同一套归一化哈希 ⇒ 该组随即满足"已有标准回答"。带 `sourceRecordId`/`sourceReplyId` 溯源。
- **「不再提示」持久化**(`backlogIgnores` 表):是标记,不是内存里的一次性过滤 —— 下次开面板仍然不提示。历史记录与标准回答都不受影响,内联二次确认明说这一点。
- **口径如实写在页面上**:分组键是**精确归一化文本匹配**,「能不能退货」与「可以退货吗」算两条 —— 语义合并留待后续版本,页面不假装合并了。
- **那条数字不并进 `GET_STATS`**:后者是聊天页内容脚本每次加载都要问一次的消息,为一行小字让它顺带做一次全表聚合,是拿**每一次页面加载**换一个页签的显示。改由沉淀页自己回传(`onCountChange`)。

### 三、导出补 kbDocs

- 信封新增 `kbDocs`(原文 + `splitterVersion` + `chunkCount`),知识块补 `chunkKind`/`sectionSeq`。
- **同 docId 跳过而非覆盖**:本地那份可能已被用户重传成新内容,拿包里更旧的版本盖回去,与全库"导入不覆盖本地编辑"的口径相悖。
- **`EXPORT_VERSION` 维持 `'2.0'`**:导入端按严格相等校验版本,**抬版本号会让旧包一个都进不来**;新增字段全部可选,旧包照常导入。
- 导入保留包内的 `splitterVersion` ⇒ 与当前不符时,SW 启动的 `resplitStaleKbDocs()` 自动重切,不必要求用户重传。

### 四、撞出来的一条真问题(单测先红)

逐条用量要"跟着条目走",于是 `deleteGolden` / `deleteKnowledge` / `deleteKnowledgeByDoc` 内部开了带 `metrics` 的事务;而 `importKbDocument`(整篇替换)与 `resplitStaleKbDocs`(自动重切)各自还套着一层外层事务,**表清单里没有 `metrics`** ⇒ Dexie 抛 `SubTransactionError: Table metrics not included in parent transaction`,**整篇重传与自动重切两条路一起断**。两处外层事务补上 `db.metrics` —— 删块时清用量键本就是同一次原子替换的一部分。这条是单测先红出来的(4 条用例),不是线上撞出来的。

## 〇-BB、2026-09-17 第五十四轮:历史问答保留期(TTL)两处修复(单测 537/537,tsc 0 错,e2e 13/13)

用户一句话:「现在历史回答记录在设置天数后过期这个逻辑正常吗」—— 先答后改,答完用户说「改+验+推」。
结论:**清理本体没问题,毛病在"什么时候清"**。清理一直没停过(靠"SW 启动后 15s"那条),坏的是另两条触发。

### 一、先验后改(不截图,数据层直读)

起真 Chromium(临时 profile、`--headless`),同 profile 反复重启,`globalThis.pddDb` 直读:

| 场景 | 实测 |
| --- | --- |
| 保留期 30,100 / 60 天前的问答 | 启动后自动清掉,**回复一并清** |
| 保留期 30,1 天前的 | 留着 |
| 200 天前的金标准 | 不动(豁免) |
| **同一条 60 天前的记录**,保留期设 90 | 留着 ⇒ 确证按**设置里的天数**走,不是写死的 |

所以"会不会按设置的天数过期"这个疑问,答案是会。真正的两条毛病:

### 二、① 每日闹钟空转(修)

`scheduleDailyAlarm()` 在 SW 顶层,每次唤醒都**无条件** `chrome.alarms.create(同名)` ——
同名 create 是**替换**,把 24h 计时从此刻重头开始。只要 24 小时内用过工具(SW 会被消息唤醒),
闹钟就被一次次推后、**永远到不了点**。真机实录:每次启动读到的都是"距现在 1440 分钟";
同名 create 当场把 `scheduledTime` 往后挪(实测 Δ≈+0.08s = 重新从 now 起算)。

**修法:幂等 —— 先 `chrome.alarms.get`,在册就原样留着,缺了才补。** 后半句不是可选项:
实测本机 Chrome **重启后不保留闹钟**(重启后读到的 `scheduledTime` 比上一轮晚 ~24s = 当轮补建),
扩展更新也会清掉闹钟,所以"装的时候建一次"不够用。修完后闹钟只作兜底(浏览器一直开着、
扩展又被晾着 24h),日常清理仍靠启动那条。

### 三、② 改保留期不立刻生效(修)

把保留期从 365 天拉到 30 天,旧记录**不会当场消失**,得等下次 SW 启动才落库。
真机复现:走真实消息路径发 `UPDATE_SETTINGS {retentionDays: 30}`,等 22 秒,90 天前那条仍在;
重启浏览器后没了 —— 与"只写在启动路径"完全对上。
(这段时间里过期记录仍可能作为检索候选出现在面板,仅本地展示;**不外发** ——
外发只带知识库候选与当前买家问题,ADR-0006 未破。)

**修法:** `UPDATE_SETTINGS` 里比对保存前后的 `retentionDays`,变了就 `await purgeIfRetentionChanged(...)`
当场清一次;没变**不触发**(清理是一次索引区间扫描,不值当每次滑杆都跑)。
清理自带兜底(失败只 `warn`、返回 0),不会把设置保存一起带崩。

### 四、顺带:抽成 `background/ttl.ts`

`runTtlPurge` / `scheduleDailyAlarm` / `purgeIfRetentionChanged` 从 `index.ts` 挪到新模块 ——
它们是"什么时候跑、跑几次"的**行为契约**,而 `index.ts` 是 SW 入口(import 即拉起整个扩展),
没法单测。这一轮的两个错正是"看不见的时序问题",留在入口里等于永远没有测试压着。

## 〇-BA、2026-09-17 第五十三轮:快捷键面板鼠标不可控(单测 530/530,tsc 0 错,e2e 全绿)

用户一句话:「目前有一个问题是,快捷键呼出的推荐回复面板,会因为鼠标悬浮在面板的某一个位置而导致悬浮处的
那条一直是选中状态。所以请你优化:快捷键呼出的面板,鼠标不可控制。」

### 症状与根因

面板弹出时指针**恰好停在某一行上**是常态(面板就开在气泡/按钮附近,鼠标本来就在那一带),
那一行随即成为选中态并**一直留着** —— 用户看到的就是"悬浮处那条一直是选中态"。
更麻烦的是**语义**:选中态决定 Enter 填哪一条,它被鼠标悄悄改写之后,用户按 Enter 拿到的那条
与他"以为自己选的那条"不是同一条。

根因是选中态当时有**两个写入口**:

- 键盘:导航键 → `movePanelSelection` → `applySelection`;
- 鼠标:`openPopup` 在键盘模式下给每一行挂了 `mouseenter` → 改 `armedPanel.selected` → `applySelection`
  —— 即 v2.6.12 引入的"鼠标悬浮同步选中,两套高亮共用一态"(当时的目的是避免 hover 底色与选中描边打架)。

### 修法:选中态收成一个写入口,悬浮回执一并关掉

① **JS 侧**:`mouseenter` 整套删除 —— 选中态只由键盘写。
② **样式侧**:四条**行级** `:hover`(候选行底色 `.pddcs-cand:hover`、操作钮显现
`.pddcs-cand:hover .pddcs-cand-actions`、整合行底色 `.pddcs-cand.pddcs-ai-row:hover`、
整合行失败态底色 `.pddcs-cand.pddcs-ai-row.is-error:hover`)统一加
`.pddcs-popup:not(.pddcs-popup-keyboard)` 守卫;键盘面板根上由 `openPopup` 挂
`pddcs-popup-keyboard` 标记类。

**为什么②不是多余的**:只删 JS 治了状态、治不了**观感** —— 悬浮行与选中行共用同一软灰填充
(`selectedBg`),指针停在哪条哪条就看着像选中,用户描述的那个现象**照样在**。两条必须一起改。

**不动的两条**:①**点击**照旧(点候选行 = 填入该条、点整合行 = 发起整合,选中行的星标/复制钮照旧点得到),
那是明确动作、不是悬浮;②**鼠标面板**(点「AI回复」打开的那种,本就没有选中态概念)的悬浮回执
一字未改 —— 守卫按**面板类型**分岔,不是"全局关掉悬浮"。

### 附带堵住的一条(比原报的那条更重)

指针停在**整合行**上时那一下 Enter,在旧实现里会从"填入候选"变成**静默发起一次付费外发请求**
(AI 整合)。ADR-0006 的口径是"AI 调用必须是一次明确动作",而这里触发它的却是"鼠标恰好停在那儿"。
该路径随本轮一并消失,e2e ⑨⑮ 锁住。

### 验收

- 单测 **530/530**(47 文件;新增 4 条,`tests/unit/ui/overlay-css.test.ts`):三处守卫各一条 +
  一条**结构不变量** —— 表里**每一条**行级 `:hover` 都必须带守卫。前三条锁当前值,第四条锁**日后**
  (新增悬浮规则时不会漏网 —— 这正是"改一处忘了另一处"最容易复发的地方)。

### ① 整合超时滑杆:两侧不同单位(真 bug,不是"滚动条坏了")

用户报的两个现象是**同一个根**:滑杆的 `value` 喂的是**毫秒**(`llmTimeoutMs` 默认 8000),
而 `min`/`max` 是**秒**(`LLM_TIMEOUT_MIN_MS/1000 = 2`、`LLM_TIMEOUT_MAX_MS/1000 = 30`)。

- 值恒大于上限 ⇒ 浏览器把滑块**钉在最右端**;
- 拖动时 onChange 给的是秒(2~30),`persistSlider({ llmTimeoutMs: v * 1000 })` 存回去又变毫秒
  ⇒ 下一帧 value 再次越界、再次被钉回右端 ⇒ 全程**看不到任何位移**,正是用户说的"拖动无变化";
- 读数走 `format(value)` = `${v} 秒`,于是显示「**8000 秒**」—— 正是"数值太高了"。

**修法:两侧同单位。** 滑杆读秒、设置仍存毫秒,**换算只在调用点一处**
(`value={draft.llmTimeoutMs / 1000}` / `onChange={(v) => persistSlider({ llmTimeoutMs: v * 1000 })}`),
顺带去掉多余的 `Math.round(v)`(step=1 本就是整数)。**没有**把 min/max 抬到毫秒 —— 读数得是用户能对上直觉的秒。

**为什么单测没拦住**:`slider.test.tsx` 只测组件自身(0.3~0.9 的量程自洽),设置页此前没有滑杆用例 ——
误差长在**调用点**上,组件测多少遍都看不见。本轮补的是一条**通用不变量**:
页面上每个滑杆**显示的数值**必须落在它自己的 `[min, max]` 里。读的是**行内格式化文本**而不是 `input.value` ——
后者在真浏览器里早被钳位到范围内,根本量不出错配。新增 `tests/unit/ui/settingsSliders.test.tsx`(4 条)。
**回归有效性反向确认过**:把 `value` 改回毫秒,三条用例当场转红(`9000 ≠ 9`),改回即绿。

### ① 面板字型立规:`design.ts#panelType`(第四件的落地)

三档**等差 2px**;字重只剩 **400 / 600**(500 在面板内退役)。五条口径:

## 〇-AW、2026-09-17 第四十九轮:推荐回复面板材料重设计(Apple 式磨砂浮层;单测 511/511,tsc 0 错,e2e 全绿)

用户原话:「你可以重新设计推荐回复面板吗。不要带着现有设计的框架,大胆一点,简约风格,类似 apple 的设计」

**口径:整体重来,不是调参。** 面板此前是「不透明白面 + 1px 描边 + 头尾两条发丝线」的工具风卡片,
四个标签页/卡片/按钮那一套语言搬到浮层上其实并不成立(浮层的任务只是"从页面上浮起来")。
本轮先把**结构**全部锁死(下方「没动的东西」一节),再放手换外观。

### 四处根本差别

1. **材料 = 磨砂面**。面板底色从 `tk.bg` 换成新令牌 `surfaceOverlay`
   (浅 `rgba(252,252,252,.80)` / 深 `rgba(28,28,30,.78)`),配
   `backdrop-filter: saturate(180%) blur(20px)`,让平台页透过面板参与成像。
   模糊半径/饱和度收在 `design.ts#material`(该文件里**唯一一个既非几何也非颜色**的令牌)。
   - **两条硬约束**:α **≥ 0.75**(再低就是"看得见后面文字"的半透明 —— 第二十三轮用户反馈过的观感;
     材料感来自**模糊**,不靠把面板做虚)且 **< 1**(等于 1 就不是材料)。两条都写进了单测。
   - **能力降级**:`overlay-css#supportsBackdropBlur()` 探 `CSS.supports`,不支持就退回 `tk.bg` 实心。
     取哪个值由纯函数 `panelSurface(tk, glass)` 单点决定 —— 因为面板底色还有一层**内联兜底**
     (`openPopup` 写入,防平台页面级 `!important` 盖掉类规则),两边必须同源,否则兜底会把材料一脚踩回不透明。
2. **描边全去**。头/尾的分隔 hairline 一起撤掉(三段只靠留白分层),面板与页面之间**唯一一条硬边**
   是 `tk.shadow` 第一段那圈 `0 0 0 0.5px`(浅色黑环 α.06 / 深色**白**环 α.10 —— 深底上画黑环等于没画)。
   阴影随之从"柔和双层"改成三段:**亮环 → 近影 → 大范围环境影**。
3. **圆角同心**。面板圆角 `radius.xl` 12 → **20px**;行圆角不再写死,由
   `ROW_RADIUS = radius.xl − ROW_INSET_X` 推出(20 − 8 = **12px**)—— 行与外壳同圆心,
   以后改外壳圆角,行自动跟随,不会两边各调一次调歪。`.pddcs-toast` 同步吃到 20px(单行时正好收成胶囊)。
4. **留白单源**。`ROW_INSET_X(8)` / `ROW_PAD_X(12)` / `ROW_PAD_Y(10)` / `ROW_GAP_Y(6)` 四个常量单点定义,
   **行距与行内节奏同取 6**;头/尾的文字内边距由 `PANEL_PAD_X = ROW_INSET_X + ROW_PAD_X = 20` 推出 ⇒
   **面板标题左缘 = 行内容左缘**(旧版 18 vs 20,差 2px;量 `rect.left + paddingLeft` 才看得出来)。

### 其余改动

- **小控件换语言**:关闭钮 / 行内图标钮 / 重试钮从"描边方钮"改为**无描边 + 全圆端(`radius.pill`)+
  安静填充(`fillQuiet` / `fillQuietHover`)**,三枚同一套形状语言;关闭钮**不悬浮也常驻可见**
  (浮层的关闭入口不该要用户先找到它)。
- **标题拆档**:「推荐回复(3)」原是挤在同一串 12.5px 灰字里的注释,拆成
  **15px semibold 标题 + 12.5px 三级灰计数**两档。
- **整合行撤描边**:只留知识库绿软底 —— 新面板里候选行静止时**都没有底**,"有底/没底"已足够区分素材与动作。
  绿底改**按主题各给一档** `knowledgeSurface`(浅 .09/.16,深 .22/.30):深色材料压在浅色平台页上
  合成出来是**中灰**(0.78×28 + 0.22×255 ≈ `rgb(78,78,79)`)而不是近黑,原来那份固定 9% 的绿到那上面
  只剩一点色偏,"这是本面板唯一的动作"就立不住了。失败面仍是固定红色字面量 —— 失败的主信号是**文字转红**,
  底色只做辅助,不必跟主题走。
- **入场动效**:160ms 淡入上移 → **220ms `cubic-bezier(.32,.72,0,1)` 淡入上移 6px + 98% 缩放**,
  `prefers-reduced-motion` 下关闭。

### 修掉的真 bug(本轮新动效引入后由 e2e 当场抓住)

**面板定位按"矮了一截"的高度算,底边压出视口。**
`getBoundingClientRect()` 返回的是**变换后**的矩形 —— 动效里那 2% 缩放让刚挂载的面板量出
378 而非 385.78,`popupPosition` 便按矮的那版夹边界;动画结束回到原尺寸时底边落到
`bottom 798.78 / vh 800`(实测断言 `面板完整落在视口内` FAIL)。
修法:量高期间 `el.style.animation = 'none'`,量完立刻还原,动效从定位好的位置开始播。
**旧版动效只翻译不缩放,所以这个坑一直没露头** —— 教训是"给浮层加 transform 类动效时,
任何 `getBoundingClientRect` 都得先关动效"。已写进 `pdd-ai-button.ts` 注释与 DESIGN.md。

### 没动的东西(重设计的边界)

行序与配额、点击填充、键盘导航(`Tab` 循环 + 默认选中**跳过整合行**)、
打开面板**不发任何请求**、ADR-0006 的外发边界(文案一字未改,仍是「点击后把命中的 N 条知识库内容
发给你配置的接口 / 只发送这条买家问题,历史回复与标准回答不出本机」)、
`pdd/ai-row.ts` 的纯逻辑与状态机 —— **一个字都没改**,本轮只换外观。

### ⚠️ 需要用户拍板的取舍:半透明

用户在**第二十三轮**("面板似半透明")与**第四十六轮**("阴影看起来像半透明边框")两次对透明表达过负面观感,
所以本轮的做法是:α 卡在 **0.80 / 0.78** + `blur(20px)`(后面文字**读不出来**,只是颜色参与成像),
并把 e2e 断言写成比"不透明"更强的契约 —— `backdropFilter` 含 `blur(20px)` **且 α ≥ 0.75 且 < 1**。
若用户仍不接受,回退点是单点的:把 `surfaceOverlay` 改成 `bg` 的值即可(或让 `panelSurface` 恒返回 `tk.bg`),
其余几何/留白/小控件语言都不依赖材料,可原样保留。

### 补修:AI 表单「保存即清空」(同日,用户报告)→ 0.12.1

用户原话:「输入模型配置后点击保存后,输入的内容会全部消失,并且不可使用」。

**根因(已实证,非猜)**:表单状态用 `{ baseUrl, apiKey, model }`,而 `PddSettings` 的三个

## 〇-AT、2026-09-17 第四十六轮:审查修复 —— 主题变量桥统一 + 首帧闪白(单测 333/333,tsc 0 错,build 过)

## 〇-AS、2026-09-16 第四十五轮:去掉 popup 外框阴影 + 文档底随主题(单测 333/333,tsc 0 错,build 过)

用户拿截图问:「主窗口圆角后方会看到半透明边框,这个边框可以去除吗,还是原生的?」

**先用像素尺定性,再改代码**(本项目处理"看着不对劲"的老规矩):拿 `scripts/measure-clip-pixels.py` 当库
(zero-dep PNG 解码;注意**该脚本末尾直接调 `main()`,当库用要 `exec` 到 `def main(` 之前**),
量用户截图(正好 420×560 = popup 尺寸)得到三条硬证据:

| 位置 | 实测 | 说明 |
|------|------|------|
| 右边/上边/下边**中段** | 全 `(255,255,255)` | **没有 1px 边框线** → 不是 border、也不是 Chrome 原生窗口边框 |
| 左边中段 | `(250,250,250)` = `bgSecondary` #FAFAFA | 导航栏底色,同样无边框线 |
| 四个角**对角线** | 左上 253→252→251→249;左下/右下 248→246→243→**235** | **由外向内渐深、到贴近圆角弧处最深** = 典型阴影梯度,不是均匀描边 |

深度也和令牌对得上:`tk.shadow = 0 1px 2px rgba(0,0,0,.05), 0 8px 24px rgba(0,0,0,.10)`;
角落最深 235 ⇒ α≈0.078(24px 模糊边缘 ≈0.7 倍 + 近影),而上方只剩偏移 0 的近影 → 最浅(249)✓。
**结论:不是原生的,是我们自己的 `boxShadow`** —— 圆角 8→24px 后,窗口四角被"切掉"的面积变大,
本来几乎看不见的阴影外溢部分就露了出来。

**修法两条(同一根因的两面)**:
1. `popup/index.tsx#App` 外层容器**去掉 `boxShadow`** —— popup 是原生窗口,外面没有可"浮起"的背景,
   阴影在窗口内唯一可见的部分就是那圈角上的溢出;浮层阴影 `tk.shadow` 令牌**保留**,只归聊天页推荐面板用。
2. `RESET_CSS` 的 `html, body { background: transparent !important }` 改为
   **`background: var(--pddcs-page-bg, #ffffff) !important`**,变量由 App 用 effect 把 `tk.bg` 写到
   `<html>` 上 —— 圆角切出来的四角读的就是这层底,不改的话**深色主题下会露出四个白角块**
   (Chrome 对透明文档默认填白)。注意 html/body **不是**根 div 的子节点,读不到挂在内层 div 的 CSS 变量桥,
   所以必须走 effect 显式写。

**验收**:像素定性(上表)+ `tsc --noEmit` 0 错 + 单测 **333/333** + `plasmo build` 过
(日志 `logs/plasmo-build-v2632.txt`)。本轮不加单测:该现象是浏览器窗口级渲染,只能靠真机像素量,
留着"用像素尺定性"这一手比写个假断言更有价值。**用户侧仍需刷新扩展**才能看到。
