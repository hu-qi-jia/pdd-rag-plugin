## 〇-HH、2026-10-19 第六十一轮:尺码整合修复(单测 949/949(72 文件),tsc 0 错,build 过)

用户实测反馈两条:①点「取消标记」时确认文案挤压;②点「根据尺码表生成回复」报
「整合结果为空,请重试」,但模型已经配置。两条都先复现了**代码路径**,不是按报错文案猜的。

### 一、「整合结果为空」:DeepSeek V4 默认开启思考模式

- **现象**:`ERROR payload.error === 'empty'`,文案来自 `AI_ERROR_TEXT.empty`。
  `empty` 只有一处产生:`llm.ts#integrateReply` 在流结束后发现 `text` 为空。
  所以不是门禁(那会是 `disabled` / `unconfigured`)、不是无材料(那会是 `no material`)、
  也不是超时/网络(那会是 `timeout` / `network`)。
- **根因**:用户配置为 `baseUrl=https://api.deepseek.com`、`model=deepseek-flash`。
  DeepSeek 自 V4 起**默认开启思考模式**(默认 effort = high),思维链通过
  `reasoning_content` 返回,与最终正文共用 `max_tokens`。请求里 256 token 的预算被思维链
  吃光后,SSE 流里只有 `reasoning_content`、始终没有 `delta.content`;而 `pickDelta`
  只取 `choices[0].delta.content` —— 于是 `text` 为空,归一成 `empty`。
  **原来的注释「不发送任何 reasoning / thinking 参数」在 V4 之后不再等于「不思考」**:
  不显式关闭,思考就是默认行为。
- **修复**:`llm.ts` 新增 `isDeepSeek()`(baseUrl 或 model 含 `deepseek`,大小写不敏感),
  对 DeepSeek 端点显式发送 `thinking: { type: 'disabled' }`;其它 OpenAI 兼容服务
  **不发**该字段 —— 各家对未知字段宽容度不一,全局发送会把别人的接口打成 400。
  知识库整合与尺码整合走同一个 `integrateReply`,因此一并修复。
- **不采用的方案**:提高 `max_tokens`。思考模式的延迟与费用都不可控,而这条路径只需要
  "照资料整合成一句话";关掉思考比给它更多预算更符合本模块的定位。

### 二、取消标记确认条挤压:flex-basis 0 不会被 flex-wrap 换行

- **现象**:截图里「取消标记后该文档恢复参与向量检索?」被压成一字一列,确认/取消钮挤在右侧。
- **根因**:`.pddcs-sizeline` 是 `display:flex; flex-wrap:wrap`,确认态下 `ConfirmRow`
  与「尺码表 / 文档名 / N 块」是同级子项。`ConfirmRow` 默认 `flex: 1` 展开为
  `flex-basis: 0` —— 父容器认为它"不占宽度",永远不触发换行,只把剩余的那点宽度分给它;
  文案于是按单字折行。
- **修复**:`ConfirmRow` 新增可选 `fullWidth`(`flex: 1 1 100%`),使确认条独占一整行;
  仅尺码表状态条传入。其它四个调用点(标准回答删除、类型删除、知识条目删除、问答删除)
  都是"确认条替换整组操作"的形态,不存在同级争宽,行为不变。

## 〇-II、2026-10-19 第六十二轮:推荐回复面板与尺码直答(单测 954/954(72 文件),tsc 0 错,build 过)

用户第二轮实测反馈三条:①选中卡片右侧常驻一块空白;②标准回答 / 历史 / 知识库三个标签要分色;
③尺码回答把买家推去「联系客服确认」,而买家要的是一个码。

### 一、右侧空白:scrollbar-gutter 的常驻槽位

- **根因**:推荐回复面板的滚动中段 `.pddcs-popup-body` 设了 `scrollbar-gutter: stable`,
  即使没有滚动条也常驻一条与滚动条等宽的槽位。选中行是**有底色**的,底色到不了这条槽位,
  于是看起来像卡片右侧缺了一块 —— 别的行没有底色,所以只有选中时才明显。
- **修复**:移除 `scrollbar-gutter: stable`。代价是滚动条出现/消失时行宽变 5~6px;
  面板只在行数超出时才滚,常驻空带比这点抖动更糟。

### 二、来源标签改为矩形 chip

- `badge()` 从 `data-tone="strong"`(只有标准回答是深色)改为 `data-kind=<kind>`,
  CSS 按来源给一套"底色 + 文字色":标准回答 = `accentSoft` + `accentText`(赭陶)、
  知识库 = 新增 `infoSoft` + `infoText`(绿)、历史 = `selection` + `textSecondary`(中性灰)。
- **形态**:从方括号终端记法(`[历史]`)改为**有底色的小矩形** —— 18px 高、圆角 4px、
  左右 6px 内边距。用户先要求分色,再明确"要矩形标签,不是 [历史] 这种";圆角特意取 4px,
  不做成胶囊(这是标签,不是按钮)。
- `infoText` / `infoSoft` 入 `ThemeTokens` 与 popup 的 CSS 变量映射;浅色 `#356B4A` / `#E7F0E9`,
  深色 `#93C2A1` / `#22302A`,文字色均按 4.5:1 下限选值。
- 原 overlay-css 里"无彩:产物里没有任何彩色"那条测试随需求作废,已替换为
  "三条 data-kind 规则各有一套可辨的底色与文字色、且不再画方括号"。

### 三、尺码必须直答:专用系统提示词

- **现象**:170cm / 55kg 的买家,模型回「体重 55kg 对应 M 码,身高 170cm 在 M 码的建议身高
  155-163cm 之外,建议联系客服确认」。
- **根因**:尺码路由虽然换的是材料(`source='size'`),但**系统提示词仍是知识库那份**。
  它的姿态是"资料没写的一律不说、判断不了用更保守的说法";在尺码语境里,这个姿态把
  "身高不在建议区间"升级成了"无法回答 → 转人工",而尺码表本身写的是"以体重为主"。
- **修复**:新增 `SIZE_SYSTEM_PROMPT`,由 `integrateReply({ source })` 选择。要点:
  1. 买家给了身高体重时**必须直接报一个具体尺码**,不能用"建议联系客服确认"代替;
  2. 明确"身高超出所选尺码的建议身高区间 ≠ 超出尺码表范围",以体重为主;
  3. 只有尺码表**明确写了**超出范围/联系客服时才那样回答;
  4. 缺身高或体重时先问,不凭空推荐;
  5. 仍只依据尺码表,仍保留 `[无法回答]` 哨兵,仍限制 60 字、无 markdown。
- 测试样本 `尺码表-女款宽松T恤.md` 同步补了一条:身高超出建议区间但体重在区间内时仍按体重选码。
  提示词与样本**两边都写**,防止模型只抓到其中一条又退回转人工。
