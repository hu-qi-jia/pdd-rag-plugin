## 一、目标与非目标

**目标**:单人客服在本地 Chrome 中使用的快捷回复扩展。自动捕获拼多多商家后台聊天页(买家问题/客服回复)→ 本地向量库;每条买家消息旁提供 AI 回复按钮,按"同一问题是否有多种回复"决定直接填充或弹窗选择;客服可把优秀回复提升为金标准(独立可编辑问答文档,归入回复文件夹),长期复用。

**非目标(v1 明确不做)**:知识库(md 上传向量化,仅占位)、多人共享/云端同步、自动发送回复、图片/语音等多模态消息、打字时前缀补全。

**姿态(合规边界)**:只记录与填充,**不替客服发送**;发送永远由客服在官方输入框点击完成;数据仅存本机 IndexedDB。

## 四、数据模型(Dexie,库名 `PddCSDB`)

### `qaRecords` 问答记录(保留期内)

| 字段 | 说明 |
|------|------|
| `id` | 主键 uuid |
| `sessionKey` | 会话标识(平台会话 id 归一化) |
| `buyerIdTail` | 买家 uid 尾号(仅去重用) |
| `question` | 合并后问题全文(买家连续文本) |
| `questionHash` | 归一化哈希(幂等/折叠用,索引) |
| `questionTs` | 问题块首条消息时间(保留期起算点,索引) |
| `embedding` / `hasEmbedding` / `embeddingModel` | 问题向量(检索锚) |
| `replyCount` | 冗余计数 |
| `createdAt` / `updatedAt` | — |

### `replies` 客服回复(候选)

| 字段 | 说明 |
|------|------|
| `id` 主键;`qaId`→qaRecords(索引) | 归属 |
| `text` / `contentHash`(归一化,索引) | 同内容折叠依据 |
| `msgId` / `ts` | 平台消息幂等键(网络层)/ 时间 |
| `embedding`/`hasEmbedding`/`embeddingModel` | v1 回复不单独向量化,预留字段 |

> v1 检索以"问题"为锚点(买家问题 vs 历史问题/金标准问题),回复文本不参与向量,但参与 BM25(辅助判定"回复内容相同性"无需)。`contentHash` 支持弹窗折叠:候选按问题召回后,回复按归一化文本分组。

### `goldens` 金标准(长期,豁免 TTL)

| 字段 | 说明 |
|------|------|
| `id` 主键;`folderId`(索引) | 归属文件夹 |
| `question` / `answer` | 可编辑双字段 |
| `qEmbedding`/`hasEmbedding`/`embeddingModel` | 问题锚向量;编辑保存时作废重嵌 |
| `sourceRecordId` / `sourceReplyId` | 提升来源(仅溯源展示) |
| `createdAt` / `updatedAt` | — |

### `folders` 回复文件夹(两层)

`id` 主键、`parentId`(null=根层,一层可挂根层)、`name`、`position`、`createdAt`。预置一条 `默认文件夹`(parentId=null;v2.6.9 前叫"未分类",存量启动时自动改名)。

### 其余

`errors`(保留)、`settings`(chrome.storage:directFillEnabled / simThreshold / retentionDays / goldenPriorityEnabled);导出信封版本升为 **2.0**。

## 五、捕获与分段流程

### 5.1 分层来源(可信度降序)

1. **网络层(主)**:MAIN-world hook `window.fetch`(匹配 `/plateau/chat/list`、`/plateau/sync/message` 等响应)与 `WebSocket` 帧;JSON 中 `from.role`(`user`/`mall_cs`)+ `msg_id` + `type`(0=文本)字段可靠。
2. **DOM(兜底)**:MutationObserver 读取新增气泡文本;方向推断与消息归属用上下文启发式(实验性,失败则记 `errors` 并降级)。

### 5.2 活跃会话规则

- 只处理**客服当前激活/渲染**的会话(页面切换会话时触发的历史接口响应即"打开会话");
- 打开即**回填**:对加载出的历史文本消息按同一分段算法处理,`msgId` 或(内容+时间)归一化键幂等去重;**消息时间早于保留期的直接跳过**;
- 会话失活/关闭时,未落盘的开放段按当前规则落盘。

### 5.3 分段算法(核心状态机)

```
会话内时间线 = 买家消息段与客服回复段交替
- buyer 文本到达:
   若当前无未结问题段 → 开新段并累加文本(合并连续买家消息,空格/换行连接)
   若已有未结问题段   → 继续累加(合并)
- agent 文本到达(消息中 from.role=mall_cs,且 type=0):
   若存在未结问题段 → 关闭问题段:落盘 qaRecords(question=累加文本)
   无论是否存在问题段 → 生成 replies 记录,挂到"本会话最近一条 qaRecords"下
     (会话内最近问题的自然归属;含"买家问题后客服迟迟回复/补发多条"情形)
- 空闲收尾:买家段打开后 3 分钟无新消息且无回复 → 落盘为"无回复问题"(保留期内仍可检索)
- 平台级重复捕获(messages 重推/历史接口重拉) → msgId 幂等去重
```

已知局限(记录在案,不阻塞):客服回复极晚且跨越了多个后续问答时,归并到"最近一条问答记录"可能与真实意图有偏差——影响面小,人工提升金标准时可修正问题字段。

### 5.4 TTL 清理

- 触发:SW 启动时 + `chrome.alarms`(新增权限)每日一次;
- 规则:删除 `questionTs`(问题产生时间)< now−retentionDays 的 qaRecords 及其 replies;独立于历史记录的金标准不受影响;清理不触碰 goldens/folders/settings。

## 六、检索、判定与 UI 状态机

### 6.1 AI 回复按钮

每条买家文本消息旁常显(半透明图标,悬停加深)。点击 → query = 该消息所属**买家问题**(合并全文)→ 混合检索。

### 6.2 混合检索(复用改造)

- 源 A:金标准(按问题向量,长驻);源 B:问答记录(问题向量×时间衰减,半衰期逻辑保留);BM25 索引重建于两源问题文本;RRF 融合 → 候选池;
- **金标准命中阈值放宽**(默认 0.4),历史命中阈值 0.5,知识库阈值独立放宽(默认 0.4,均可设置);
- 候选**回复内容折叠**:按 `contentHash` 分组,相同回复只留一条,取组内最高分/最新时间;金标准与历史同文本 → 显示金标准(徽标优先);
- 候选附带来源(金标准/历史回复)+ 原始问题摘要展示。

### 6.3 状态机

```
点击 AI 按钮
 ├─ 无候选过阈值 → 轻提示"无匹配,请手动回复"(不改输入框)
 ├─ 直接填充开关 = 开
 │    └─ 按 金标准 > 知识库(空)> 历史 取最高分候选
 │         └─ ≥ 阈值 → 填充输入框 + 来源标注;否则不填 + 提示
 └─ 直接填充开关 = 关
      ├─ 折叠后候选 = 1 条(过阈值)→ 直接填充 + 来源标注
      └─ 折叠后候选 ≥ 2 条 → 候选弹窗 top-k=3
           (金标准置顶+金色徽标,其余按得分降序)
           每条含:回复正文、来源、原始问题摘要、[设为金标准](默认入"默认文件夹")
           点击 → 填充输入框;弹窗内亦可"仅复制"
```

填充动作 = 写入官方输入框 DOM(触发 React 受控输入所需的事件序列)+ 来源气泡提示;**不点发送**。

### 真机抓帧校准发现(2026-09-08,CDP 实测,已修)

原设计假设聊天消息经 m-ws WebSocket 推送,经抓帧发现**全错位**,已按实测修正:

1. **聊天消息完全不走 WebSocket**——m-ws 连接只发 auth 帧;titan-ws 是二进制 protobuf 通知(新消息提醒等,未解码);买家消息通过 **HTTP 轮询 `/plateau/chat/list`** 拉取,`/plateau/sync/message` 触发同步;
2. **所有聊天接口走 XMLHttpRequest**(send_message / chat/list / mark_read / sync),非 fetch → hook 已补 `patchXhr`(原型 open/send 旁路,load 时读 responseText);
3. **消息帧无 session_id**——会话键 = 消息 from/to 中 role=user(买家)一侧的 uid(客服侧 uid= mall_id);`pickSessionKey` 已加该兜底;
4. **`ts` 是字符串**(秒级"1788860669",亦见毫秒串)——解析器需接受数字字符串并做秒→毫秒换算;
5. 真机帧形态:`{from:{uid,role},to:{uid,role},type:0,content,msg_id,client_msg_id,ts,status}`;测试已补 3 例真机结构用例(37/37 绿);
6. 客服发出文本在 send_message **请求体**(响应无回显文本)→ 请求体解析(chat URL 命中)为发出消息主通道,轮询响应为买家消息主通道;
7. 校准期间注入范围临时放宽为 `mms.pinduoduo.com/*` + `all_frames`,链路稳定后收回 `chat-merchant*` 顶层(记录于代码注释)。
